## 1. Что такое паттерн проектирования

**Паттерн проектирования** — это именованное типовое решение часто встречающейся
задачи проектирования. Это не готовая библиотека и не кусок кода, который можно
вставить в проект. Это описание ролей, связей и взаимодействия объектов, которое
много раз доказало свою пользу.

Паттерны делят на три группы:

- **порождающие** — как создавать объекты (`Factory Method`, `Builder`, `Singleton`);
- **структурные** — как собирать объекты в более крупные структуры (`Adapter`, `Decorator`, `Facade`);
- **поведенческие** — как объекты распределяют поведение и общаются (`Strategy`, `Observer`, `Command`).

`Strategy` — поведенческий паттерн.

Зачем вообще паттерны:

1. Дают общий язык: «здесь нужен Декоратор» короче, чем полстраницы объяснений.
2. Помогают не изобретать архитектуру заново.
3. Делают код расширяемым: новое поведение добавляется, а старое не ломается.

Паттерн — это не «любая красота в коде». Если задача маленькая и вариантов
поведения нет, паттерн может быть лишним усложнением.

## 2. Что такое паттерн «Стратегия»

### Проблема

Есть несколько алгоритмов одной задачи. Например, несколько перевозчиков считают
стоимость по-разному. Если написать это через `if/else` или `switch`, то:

- один большой метод знает все тарифы сразу;
- при добавлении нового перевозчика приходится менять уже работающий код;
- чем больше вариантов, тем длиннее и опаснее `switch`;
- разные тарифы трудно тестировать по отдельности.

### Идея

Вынести каждый алгоритм в отдельный класс. У всех классов один общий интерфейс.
Клиентский код работает не с конкретным классом, а с интерфейсом. Конкретный
алгоритм можно подставить во время работы программы.

### Роли

| Роль | В задании |
|---|---|
| **Strategy** — общий интерфейс алгоритмов | `DeliveryStrategy` |
| **ConcreteStrategy** — конкретные алгоритмы | `WeightStepDelivery`, `VolumeDelivery`, `ZoneDelivery`, `ExpressDelivery` |
| **Context** — хранит стратегию и делегирует ей работу | `DeliveryCalculator` |
| **Client** — выбирает и подставляет стратегию | `DeliveryCalculatorFactory`, `Main` |

Схема:

```
Main / Demo
    │
    ▼
DeliveryCalculator  ──────►  DeliveryStrategy (интерфейс)
    │                              ▲
    │                              │
    │              ┌───────────────┼───────────────┬──────────────────┐
    │              │               │               │                  │
    │     WeightStepDelivery  VolumeDelivery  ZoneDelivery  ExpressDelivery
    │
    └── хранит List<DeliveryStrategy>
```

### Что важно понять

Стратегия — это **не просто функция**. В задании перевозчик несёт собственную
тарифную сетку, свои пределы, своё имя для вывода и умение отказаться с
объяснением. Поэтому это полноценный класс с поведением и данными, а не
`Map<String, Function>`.

### Плюсы

- **Open/Closed Principle**: новый перевозчик добавляется новым классом, а не
  правкой старого `switch`.
- **Single Responsibility**: каждый класс отвечает за один тариф.
- Легко тестировать каждый тариф отдельно.
- Легко добавить новый вариант, не трогая расчёт и вывод.

### Минусы

- Классов становится больше.
- Клиент должен как-то выбрать и создать стратегию.
- Если вариант всего один и не планируется расширение, паттерн избыточен.

## 3. Тарифы и решения по границам

| Перевозчик | Формула | Предел |
|---|---|---|
| По весу (ступени) | до 1 кг — 300; до 3 кг — 550; до 5 кг — 750; свыше — 750 + 150 × (начатых кг сверх 5) | вес > 30 кг — отказ |
| По объёму | `max(250, 900 × объём)` | объём > 5 м³ — отказ |
| По зонам | Город — 300; Область — 600; остальные — 1200 | Заграница — отказ |
| Экспресс | 900 + 100 × (начатых кг) | без предела |

### Осознанные решения

1. **Границы ступеней включительные.** Ровно 1 кг — 300, ровно 3 кг — 550,
   ровно 5 кг — 750. Это выбрано специально и проверено тестами. В задании
   сказано, что решение может быть любым, но должно быть осознанным.
2. **«Начатый килограмм» — это `Math.ceil`, а не `(int)`.** 5.01 кг — это один
   начатый килограмм сверх пяти, 6.0 кг — тоже один, 6.01 кг — уже два.
   Поэтому 5.01 кг стоит 900, 6 кг — 900, 6.01 кг — 1050.
3. **Если все отказались**, `findBest` возвращает `null`, а `Main` печатает
   «никто не берётся». Это не ошибка программы, а нормальный исход.
4. **Ничья.** Если два перевозчика дали одинаковую минимальную цену, побеждает
   тот, который был добавлен раньше. В задании ничья не описана, поэтому правило
   зафиксировано в коде и комментарии.

| Файл | Роль |
|---|---|
| `Parcel.java` | Параметры посылки: вес, объём, зона. Неизменяемый объект. |
| `DeliveryStrategy.java` | Интерфейс стратегии: имя, причина отказа, цена. |
| `WeightStepDelivery.java` | Тариф по ступеням веса. |
| `VolumeDelivery.java` | Тариф по объёму. |
| `ZoneDelivery.java` | Тариф по зонам. |
| `ExpressDelivery.java` | Экспресс-тариф. |
| `DeliveryOffer.java` | Результат одного перевозчика: цена или отказ. |
| `DeliveryCalculator.java` | Контекст: список стратегий, расчёт всех цен, выбор лучшей. |
| `DeliveryCalculatorFactory.java` | Собирает стандартный набор перевозчиков в одном месте. |
| `Main.java` | Ввод параметров, вывод всех цен и победителя. |
| `Demo.java` | Несколько готовых посылок, чтобы показать разных победителей. |

Старая версия кода сохранена в `src_backup_original` — она не участвует в сборке,
потому что лежит вне `src`.

> Первый коммит в Git — это исходная незавершённая версия. Она не компилируется:
> в `DeliveryCalculator` был разорван `else if`, а в `VolumeDelivery` потерян
> `return`. Это сохранено специально, чтобы в истории было видно, с чего
> начиналась работа. Следующие коммиты постепенно приводят проект к рабочему

## 5. Как запустить

### В IntelliJ IDEA

Открыть проект и запустить один из классов:

- `Main` — интерактивный ввод;
- `Demo` — готовые примеры;
- `SelfTest` — тесты.

### Из консоли

```bash
javac -encoding UTF-8 -d out src/*.java

java -cp out Main
```

`.idea/encodings.xml`, чтобы IDEA тоже читала файлы как UTF-8.

## 6. Как добавить нового перевозчика

1. Создать класс, который реализует `DeliveryStrategy`.
2. Добавить одну строку в `DeliveryCalculatorFactory.createStandard()`.

Например:

```java
public class DroneDelivery implements DeliveryStrategy {
    @Override
    public String getName() {
        return "Дрон";
    }

    @Override
    public String getRefusalReason(Parcel parcel) {
        if (parcel.getWeight() > 2.0) {
            return "дрон берёт не больше 2 кг";
        }
        return null;
    }

    @Override
    public int calculate(Parcel parcel) {
        String refusal = getRefusalReason(parcel);
        if (refusal != null) {
            throw new IllegalStateException("Нельзя считать цену при отказе: " + refusal);
        }
        return 1500;
    }
}
```

И в фабрике:

```java
calculator.addStrategy(new DroneDelivery());
```

`DeliveryCalculator`, `Main` и `Demo` при этом не меняются. Это и есть главный
смысл паттерна.

## 7. Вопросы, которые могут задать на защите

**Почему интерфейс, а не абстрактный класс?**
В Java интерфейс — минимальный контракт без состояния. У стратегий нет общего
поля, которое нужно наследовать, поэтому интерфейса достаточно. Абстрактный класс
был бы оправдан, если бы у всех перевозчиков был общий код или общее состояние.
В Python, где интерфейсов нет, ту же роль играет абстрактный базовый класс.

**Почему не `switch` по названию перевозчика?**
Потому что тогда добавление нового перевозчика меняет существующий метод.
Это нарушает Open/Closed Principle и повышает риск сломать уже работающие тарифы.
Со стратегиями старый код не трогается.

**Где выбирается стратегия?**
В `DeliveryCalculatorFactory` — это композиционный корень. В `Main` мы получаем
уже готовый калькулятор. Во время работы калькулятор перебирает список стратегий
и выбирает лучшую по цене.

**Почему `calculate` выбрасывает исключение при отказе?**
Контракт такой: сначала `getRefusalReason`, и только если там `null`, вызывается
`calculate`. Калькулятор так и делает. Исключение — защита от неправильного
вызова, чтобы не вернуть молча 0 и не спутать «бесплатно» с «отказался».

**Почему `Math.ceil`, а не `(int)`?**
`(int)` отбрасывает дробную часть: 5.01 превратилось бы в 5, и лишний начатый
килограмм потерялся бы. `Math.ceil(5.01 - 5) = 1` — правильно.

**Почему `List`, а не `Map<String, Function>`?**
Стратегия — это не только функция. У неё есть имя, предел, причина отказа и
тарифная сетка. `Map` из лямбд потерял бы типобезопасность и объектную структуру,
а добавление нового поведения снова потребовало бы правки общей таблицы.

**Что будет, если все отказались?**
`findBest` вернёт `null`. `Main` выведет сообщение, что никто не берётся.
Это ожидаемый сценарий, а не исключение.

**Что будет при ничьей?**
Победит первый добавленный перевозчик. Правило зафиксировано в комментарии
`findBest`; в задании ничья не оговорена.

## 8. Что проверяет `SelfTest`

Тесты написаны на чистой Java, без JUnit и любых других библиотек. Причина
простая: в окружении, где собирался проект, не было ни интернета, ни локального
`junit.jar`. Поэтому вместо аннотаций используется обычный `main`, а вместо
`assert` — маленькие методы `checkEquals` / `checkTrue` / `checkThrows`.
Один упавший тест печатает `FAIL` и в конце даёт код возврата 1.

Что покрыто:

- **Happy path** — по одной обычной посылке на каждый тариф.
- **Границы веса**: 1, 1.01, 3, 3.01, 5, 5.01, 6, 6.01, 30, 30.01 кг.
- **Границы объёма**: 0.01, 0.1, 0.5, 1, 5, 5.01 м³ (включая минимум 250 руб.).
- **Зоны**: Город, город, « ГОРОД », Область, ОБЛАСТЬ, Деревня,
  Заграница, ЗАГРАНИЦА.
- **Экспресс**: 0.1, 1, 1.01, 3, 3.01, 6 кг и проверка, что он никогда
  не отказывается.
- **Выбор победителя** для четырёх разных посылок.
- **Ничья**: при равной цене побеждает тот, кого добавили раньше (проверяется
  в обоих порядках).
- **Инварианты калькулятора**: `null`-стратегия и `null`-посылка запрещены,
  список предложений неизменяемый снаружи, пустой калькулятор не падает,
  «все отказались» даёт `null`.
- **Контракт стратегии**: `calculate` для отказавшей посылки бросает
  `IllegalStateException`.
- **Валидация посылки**: отрицательный и нулевой вес, нулевой и отрицательный
  объём, пустая зона, зона из пробелов, `null`-зона; обрезка пробелов.
- **Инварианты `DeliveryOffer`**: у принятого нет причины отказа и есть цена,
  у отказанного цена 0 и есть причина.

Ожидаемый результат: `Итого: пройдено 76, провалено 0`.

> В истории Git есть коммит с JUnit-версией тестов. От неё пришлось отказаться:
> без сети и без локального репозитория Maven/Gradle `org.junit.jupiter.api`
> просто неоткуда взять, и проект переставал компилироваться. Это честный след
> эволюции решения, а не потерянная работа.
